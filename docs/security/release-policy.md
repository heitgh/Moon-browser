# Política de atualização e publicação

Meta de manutenção para versões distribuídas: incorporar correções **críticas** do Electron/Chromium em até **cinco dias úteis** após uma versão corrigida compatível ficar disponível. Falhas graves no próprio Moon exigem triagem no mesmo dia útil e podem exigir suspender downloads até sair uma correção. Esta meta deve ser medida por release, com data do aviso, versão do Electron/Chromium e resultado dos gates; não significa que a alpha atual já esteja homologada.

Os canais são `stable` (sem sufixo) e `beta` (`-beta.N`); `alpha` permanece experimental. O verificador não oferece alpha a beta nem prerelease a stable. Não há downgrade automático. Se uma versão falhar, retire o release do feed, publique uma versão maior corrigida e forneça instruções de restauração manual. O backup SQLite antes de instalar **não** inclui cookies nem partições Chromium. Não há rollback transacional de instalador.
O download diferencial está desativado no código atual: a verificação de assinatura Ed25519 cobre o AppImage completo e a economia de banda não compensa perder um caminho de verificação simples antes de homologar o updater.

## Gate de publicação

1. Bump de versão e notas, lockfile íntegro, CI Windows/Linux, E2E, `npm audit --audit-level=high`, SBOM CycloneDX e fuses verificados.
2. Windows: certificado Authenticode de uma autoridade confiável provisionado via `WINDOWS_CSC_LINK`/`WINDOWS_CSC_KEY_PASSWORD`, nome distinto completo em `WINDOWS_PUBLISHER_NAME`; `forceCodeSigning` e `Get-AuthenticodeSignature` devem passar para o instalador, o portátil e o executável interno. Confirmar `publisherName` no `app-update.yml` empacotado. Assinatura válida identifica o publicador; o SmartScreen pode continuar avisando até o certificado e os downloads adquirirem reputação. Não contornar o aviso removendo verificações ou solicitando exceções aos usuários.
3. Linux: `LINUX_GPG_PRIVATE_KEY_B64`, `LINUX_GPG_FINGERPRINT`, `LINUX_GPG_PASSPHRASE` e chave Ed25519 `LINUX_UPDATE_SIGNING_KEY_B64` provisionadas fora do Git. O build embute a chave pública Ed25519; o workflow assina AppImage, pacotes, checksum, SBOM e manifesto, e verifica tudo antes de publicar. O atualizador do AppImage exige a assinatura Ed25519 do arquivo recebido. A assinatura GPG permite verificação independente dos downloads; não cria, por si só, um repositório apt/rpm assinado.
4. Executar `workflow_dispatch` na branch `main`, com `prepare_signed=true`, `publish_release=false` e tag exatamente igual à versão do código. Este ensaio gera artefatos assinados de 14 dias para homologação, sem criar release pública. PRs executam builds de teste sem segredos. O acesso de leitura aos nomes dos segredos via API não comprova sua configuração; o ensaio deve passar nos próprios runners.
5. Testar instalação, upgrade da versão anterior, interrupção de download, certificado inválido, restauração e remoção em máquinas Windows/Linux reais usando os artefatos do ensaio. Registrar a versão de origem, sistema, assinatura observada e resultado. Para macOS/ARM, exigir workflow, assinatura e notarização próprios antes de declarar suporte.
6. Só depois executar `workflow_dispatch` em `main` com `publish_release=true`. O workflow recusa release existente, tag divergente e artefatos incompletos. O ambiente `release-approval` continua sendo um gate do GitHub configurado fora do repositório. Usar as mesmas chaves do ensaio; qualquer troca de chave Ed25519 exige um plano explícito de migração, pois a chave pública está embutida no AppImage anterior.

## Migração do feed legado

A `v0.6.0-alpha.7` usa os manifestos `alpha.yml`/`alpha-linux.yml` e não verifica uma assinatura Ed25519 independente do AppImage baixado. A primeira release assinada usa `signed-alpha.yml`/`signed-alpha-linux.yml` (e equivalentes `signed-beta`/`signed-latest` no futuro). **Não publicar os manifestos legados** junto à nova release. Assim, a instalação `alpha.7` deve oferecer a página oficial como caminho de atualização manual; o primeiro upgrade nativo com assinatura de ponta a ponta começa a partir da `alpha.8` assinada. Verificar este fluxo em Windows e Linux antes de anunciar a release. Essa transição preserva a opção de atualizar, mas exige uma instalação manual única.

Chaves comerciais não são incluídas no repositório. Sem elas, o código pode gerar build de teste, mas **nenhuma release assinada deve ser anunciada**. Builds de desenvolvimento sem raiz de confiança não disponibilizam instalação nativa pelo atualizador.
